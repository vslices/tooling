# VSlices Tooling v0.2.0-preview

This document defines the current intended scope and release-readiness direction for `v0.2.0-preview`.

`v0.2.0-preview` is not defined by one mandatory headline feature. It is the next evolutionary line of the CLI after the conservative deterministic baseline established by `v0.1.x-preview`.

The current work has two complementary tracks:

```text
CLI experience
  -> make the existing tooling easier to identify, read, and operate

semantic capability
  -> represent and lower progressively richer VSIR cases until concrete evidence exposes genuinely interpretive work
```

The current candidate for that later interpretive surface remains:

```text
vslices interpretate
```

but the command should emerge from a concrete case that requires it. The version does not require an interpretive mechanism merely to satisfy a roadmap label.

## Current implementation order

The intended sequence is deliberately incremental:

```text
1. expose reliable CLI identity
   -> --version
   -> -v

2. establish a small static terminal presentation boundary
   -> semantic presentation roles
   -> Kokuban rendering
   -> Kurukuru progress where appropriate

3. expand VSIR coverage through concrete domain/software examples

4. classify newly encountered materialization decisions
   -> deterministic
   -> rebase-compatible
   -> genuinely underdetermined but constrained
   -> unsupported

5. introduce interpretate only when a concrete constrained case cannot be faithfully completed by deterministic mechanisms
```

This ordering treats interpretive lowering as a discovered requirement rather than an assumed destination.

## CLI experience track

The first adopted additions are CLI identity and a presentation boundary.

### Version identity

The CLI exposes:

```text
vslices --version
vslices -v
```

Both forms must produce the same user-facing identity.

Published versions use their product version, while pull-request builds preserve the build identity established by the `v0.1.1-preview` distribution work:

```text
0.2.0-preview
build3.172
```

A technical assembly representation such as:

```text
0.0.0-build.3.172
```

is a .NET materialization detail and should not leak into normal CLI output.

### Static terminal presentation boundary

Commands should progressively stop encoding presentation decisions directly through scattered `Console.WriteLine` calls.

The initial boundary is intentionally small and static. It represents roles such as:

```text
Heading
Info
Success
Warning
Error
Muted
Progress
```

The current renderer may use Kokuban for styled text and Kurukuru for interactive progress, but those libraries are implementation details rather than VSlices command semantics.

A guiding rule is:

> Presentation may decorate command output. Presentation must not change command semantics.

Machine-consumable output must remain safe to redirect. Progress indicators must not contaminate redirected stdout.

Custom themes are a possible future extension, but `v0.2.0-preview` does not require a user-configurable styling system. The static boundary should first prove which presentation roles are actually useful.

## Deterministic baseline preserved

The `v0.1.x-preview` line established:

```text
transpile
  = deterministic lowering from VSIR to a target materialization

rebase
  = deterministic integration of a VSIR change over a human-modified materialization when ancestry is available

lower
  = orchestration that selects the least-powerful sufficient mechanism
```

These authority boundaries remain intact while `v0.2.0-preview` expands the represented cases.

A missing lowering rule remains a reason to stop rather than permission to improvise.

## Discovery through broader VSIR coverage

The main semantic-development strategy for this preview is to represent more real concepts and exercise them through the existing lowering pipeline.

For each new `.vsir`, the project should ask:

```text
Can the semantics be represented faithfully?
Can the current ruleset lower them deterministically?
Can target tooling authoritatively resolve the remaining target detail?
Can rebase preserve compatible human choices?
What, if anything, remains underdetermined?
```

New structures should be added because a concrete case requires them, not to pre-design a universal IR.

This process may produce:

- new VSIR structures;
- new deterministic rules;
- clearer target-context delegation;
- stronger conformance obligations;
- new rebase cases;
- evidence that a previously suspected interpretive case is actually deterministic;
- eventually, evidence for an interpretive lowering mechanism.

## Interpretive lowering hypothesis

If a concrete materialization decision cannot be completed by deterministic transpilation or deterministic semantic rebase, `interpretate` becomes relevant only when the available VSIR, ruleset, target context, and project evidence still provide enough authority to constrain a valid result.

A useful shorthand remains:

> Interpretation may resolve underdetermined materialization. Interpretation must not manufacture missing authority.

The invalid fallback remains:

```text
no deterministic rule
  -> let a model guess
```

Instead:

```text
no rule or no declared interpretive authority
  -> unsupported / unresolved
  -> stop
```

If interpretive lowering is adopted, the intended power ordering is:

```text
transpile
  < rebase
  < interpretate
```

and `lower` continues to select the least interpretive sufficient mechanism.

## Candidate interpretive authority

A future constrained/interpretive rule is expected to communicate enough authority to determine:

- what semantic operation is being materialized;
- what must be preserved;
- what implementation freedom is allowed;
- what is prohibited;
- what contextual evidence may be consulted;
- what conditions make a candidate materialization acceptable.

The exact schema is intentionally not frozen in advance.

The mechanism performing the interpretation is also not part of the semantic contract. Evidence may eventually favor deterministic search, target tooling, an LLM, another model, or a hybrid.

## Candidate benchmark direction

`StreetExtension.vsir`, including `split-first-rest`, remains an interesting benchmark because its construction refinement exposes non-trivial obligations.

However, it is not assumed to require `interpretate`.

If a faithful deterministic lowering convention can satisfy the obligations, it should remain deterministic. Interpretation exists for genuine underdetermination, not to preserve complexity.

As broader VSIR examples are introduced, a better first interpretive benchmark may emerge.

## Context and target authority

When target tooling already owns a materialization decision, VSlices should consult or delegate to that tooling before duplicating the decision.

For C#/.NET, candidate authorities remain:

```text
semantic meaning
  -> VSlices / VSIR / ruleset

project and item context
  -> dotnet / MSBuild / template conventions

syntax
  -> Roslyn

formatting
  -> dotnet format / Roslyn

compilation
  -> dotnet build

technical tests
  -> dotnet test
```

Interpretive reasoning should operate only on the residual decision that these authorities do not already determine.

## Explicit non-scope

Unless separately justified by concrete evidence, `v0.2.0-preview` does not require:

- a generic autonomous coding agent;
- automatic semantic invention when rules are incomplete;
- a provider/plugin marketplace for AI models;
- repository-wide autonomous refactoring;
- arbitrary remote execution;
- a universal final schema for interpretive rules;
- a fully configurable terminal theme system;
- new production-ready target languages;
- `vslices update --ruleset`;
- automatic provenance reconstruction for every rebase scenario.

## Release-readiness direction

The exact final release boundary remains revisable while the preview evolves, but the adopted line should preserve these properties:

- all `v0.1.x-preview` deterministic behavior remains intact;
- `--version` and `-v` expose the same correct user-facing identity;
- PR builds expose `build<pr>.<run>` rather than leaking their internal assembly version;
- terminal presentation is centralized behind a small semantic boundary;
- redirected/machine-consumable output remains clean;
- Native AOT publication remains green on the supported RIDs;
- install, PR-build, and self-update workflows continue to function;
- new VSIR structures are justified by concrete examples;
- missing lowering knowledge still fails explicitly;
- if `interpretate` is adopted, at least one concrete benchmark demonstrates that deterministic mechanisms are genuinely insufficient;
- any adopted interpretive mechanism is explicitly authorized and constrained rather than acting as a missing-rule fallback;
- documentation distinguishes implemented behavior from hypotheses and future direction.

## Research questions

The preview should use implementation evidence to answer questions such as:

1. Which presentation roles are actually useful enough to preserve as a stable terminal boundary?
2. Which additional real-world concepts expose the next useful VSIR structures?
3. Which apparently complex lowering decisions collapse into deterministic rules after enough target context is modeled?
4. What is the first decision that remains genuinely underdetermined while still being semantically constrained?
5. What is the smallest useful representation of interpretive authority for that case?
6. What mechanism is sufficient to resolve it?
7. What evidence must be retained so the result is reconstructible?
8. When should a successful interpretive pattern be promoted into a deterministic lowering rule?

## Version intent

`v0.2.0-preview` is an evolutionary preview line, not a promise of an eventual stable `v0.2.0` release.

Its continuity requirement is stronger than any individual feature commitment: the tooling may gain richer presentation and richer lowering mechanisms, but it must continue to distinguish semantic authority from implementation freedom and must not turn missing knowledge into implicit permission to guess.
