# VSlices Tooling v0.2.0-preview

This document defines the current intended scope and release-readiness criteria for `v0.2.0-preview`.

The purpose of `v0.2.0-preview` is to introduce the first explicit interpretive lowering surface without weakening the authority boundaries established by the `v0.1.x-preview` line.

The candidate theme is:

```text
vslices interpretate
```

`interpretate` exists for materialization decisions that cannot be completed by deterministic transpilation or deterministic semantic rebase, but for which the available VSIR, ruleset, target context, and project evidence still provide enough authority to constrain a valid result.

It is not a fallback for missing semantic knowledge.

## Core boundary

The `v0.1.x-preview` line established this policy:

```text
transpile
  = deterministic lowering from VSIR to a target materialization

rebase
  = deterministic integration of a VSIR change over a human-modified materialization when ancestry is available

lower
  = orchestration that selects the least-powerful sufficient mechanism
```

`v0.2.0-preview` adds:

```text
interpretate
  = constrained interpretive lowering when deterministic mechanisms are insufficient but semantic authority is still sufficient
```

The intended ordering remains:

```text
transpile
  < rebase
  < interpretate
```

where the ordering represents increasing interpretive power rather than importance.

`lower` should continue to select the least interpretive sufficient mechanism.

## What interpretive lowering is

Interpretive lowering may resolve implementation choices when all of the following are true:

1. the semantic operation is already represented by VSIR;
2. the ruleset explicitly permits interpretive resolution for that operation or materialization decision;
3. the ruleset provides enough obligations, permissions, prohibitions, or equivalent constraints to define the acceptable result space;
4. the required target/project context is available;
5. the resulting materialization can be checked against the known constraints.

A useful shorthand is:

> Interpretation may resolve underdetermined materialization. Interpretation must not manufacture missing authority.

The following remains invalid:

```text
no deterministic rule
  -> let a model guess
```

Instead:

```text
no rule or no declared interpretive authority
  -> unsupported / unresolved
  -> stop
```

## Candidate executable surface

The first candidate command is:

```text
vslices interpretate <vsir>
```

The exact option surface remains subject to concrete implementation evidence.

The command should reuse the same artifact discovery, target resolution, project configuration, target context, file-safety guarantees, and ruleset registry used by deterministic lowering rather than constructing an independent execution path.

`interpretate` should not imply a specific model provider, cloud service, or model family in its public semantic contract.

## Ruleset authority

The ruleset remains the authority that determines whether a materialization decision is:

```text
deterministic
constrained / interpretive
unsupported
```

The exact schema for constrained rules is intentionally not frozen by this document. Concrete examples should drive the shape.

A constrained rule is expected to be able to express, directly or through equivalent structures:

- what semantic operation is being materialized;
- what must be preserved;
- what implementation freedom is allowed;
- what is prohibited;
- what contextual evidence may be consulted;
- what conditions make the interpretation valid or invalid.

The executable may provide the mechanism that evaluates and applies those rules, but new lowering knowledge should remain externalizable whenever practical.

## First benchmark direction

The current best candidate benchmark is `StreetExtension.vsir`, specifically the construction refinement around `split-first-rest` and subsequent state establishment.

That case is useful because it already exposes a materialization decision with meaningful obligations:

- preserve construction order;
- preserve the declared refinement operation;
- preserve exact semantic bindings;
- preserve failure semantics;
- preserve subsequent use of the refined bindings;
- do not introduce new validation, normalization, side effects, or semantic state.

This benchmark should not predetermine that `split-first-rest` must remain interpretive forever. If a faithful deterministic lowering convention is discovered and adopted, the operation should become deterministic instead.

Interpretation exists for genuine underdetermination, not to protect complexity from simplification.

## Context acquisition

Interpretive lowering may require evidence beyond the VSIR document itself.

Candidate evidence sources include:

- the project-local ruleset;
- the current target project and directory;
- existing target-language materializations;
- target tooling such as `dotnet`, MSBuild, or Roslyn where those tools are authoritative for target-specific facts;
- explicitly supplied ancestry or related project artifacts.

Context acquisition must remain scoped to the decision being resolved. `interpretate` should not turn into an unconstrained repository-wide research agent merely because contextual reasoning is available.

When target tooling already owns a materialization decision, VSlices should consult or delegate to that tooling before duplicating the decision interpretively.

## Result and evidence

An interpretive operation should make its basis reconstructible enough to distinguish a constrained resolution from an unexplained guess.

The exact evidence format is not yet fixed, but the preview should establish at least enough observable information to answer:

```text
Why was interpretate selected?
Which rule authorized interpretation?
Which contextual evidence materially affected the result?
Which obligations were checked before accepting the materialization?
```

This may initially be represented through diagnostics or command output rather than a permanent provenance subsystem.

## Relationship with lower

`lower` remains the normal orchestration surface.

The intended policy becomes:

```text
new VSIR + deterministic rules sufficient
  -> transpile

changed VSIR + human materialization + sufficient ancestry
  -> rebase

materialization decision not deterministically resolvable
+ explicit interpretive authority
+ sufficient context
  -> interpretate

missing semantic authority or insufficient context
  -> stop
```

`lower` must not choose `interpretate` merely because it is capable of producing an answer.

## Explicit non-scope

Unless separately adopted through concrete evidence, `v0.2.0-preview` does not require:

- automatic semantic invention when the ruleset is incomplete;
- a general-purpose autonomous coding agent;
- a provider/plugin marketplace for AI models;
- arbitrary remote execution;
- repository-wide autonomous refactoring;
- automatic provenance reconstruction for all rebase scenarios;
- `vslices update --ruleset`;
- new production-ready target languages;
- a stable universal schema for every future interpretive rule;
- a claim that all constrained rules require AI or an LLM;
- semantic verification of arbitrary source code beyond the obligations required by the adopted benchmark cases.

The preview should prefer one narrow faithful interpretive case over a broad mechanism whose authority cannot be explained.

## Release-readiness criteria

`v0.2.0-preview` should not be tagged until the adopted branch demonstrates all of the following:

- the `v0.1.x-preview` deterministic behavior remains intact;
- `vslices interpretate` exists as an explicit command or an equivalent adopted surface;
- at least one concrete VSIR/materialization case genuinely requires interpretive resolution under the adopted ruleset;
- the relevant ruleset entry explicitly distinguishes interpretive authority from missing-rule failure;
- the interpretive mechanism cannot activate when no rule authorizes it;
- the implementation preserves the adopted obligations, permissions, and prohibitions for the benchmark case;
- `lower` selects `interpretate` only after deterministic mechanisms are shown insufficient for that case;
- target/project context consulted by interpretation is explicit and bounded;
- failures remain values/diagnostics rather than silent guesses;
- automated tests exercise both a successful constrained interpretation and refusal when authority/context is insufficient;
- Native AOT publication and the existing install/update flows remain green;
- PR build artifacts continue to provide a practical way to test the new command before a tagged preview;
- documentation distinguishes implemented behavior from hypotheses and future direction.

## Research questions for the preview

The following questions are intentionally open and should be resolved through implementation evidence rather than assumed in advance:

1. What is the smallest useful schema for expressing constrained lowering authority?
2. Which parts of an interpretive rule belong in executable YAML versus human-readable documentation?
3. What target/project context is necessary for the first benchmark, and what context would be excessive?
4. What mechanism should perform the interpretation: deterministic search, target tooling, an LLM, or a hybrid?
5. What minimum evidence should be retained so the resolution is reconstructible?
6. What checks are sufficient to reject a materially non-conformant interpretation?
7. At what point should a successful interpretive pattern be promoted into a deterministic lowering rule?

## Version intent

`v0.2.0-preview` is an evolutionary preview boundary, not a promise of an eventual stable `v0.2.0` release.

The scope may be revised as concrete experiments expose better boundaries.

The continuity requirement is stricter than the feature requirement: the version may narrow or change its interpretive mechanism, but it should not weaken the principle that VSlices may complete materialization choices only within authority already established by semantic source, rules, context, and target tooling.
