# VSlices Tooling v0.2.0-preview

`v0.2.0-preview` is an evolutionary preview line. It expands CLI operability and semantic capability from concrete consumer evidence while preserving authority boundaries.

> Lowering may complete implementation detail. Lowering must not complete missing semantics.

## Consolidated lowering architecture

The current internal flow is:

```text
CLI command adapter
  -> operation / coordinator
  -> project / ruleset / lineage infrastructure
  -> VSIR / target mechanisms
```

`TranspilationOperation` owns deterministic projection, `RebaseOperation` owns deterministic three-way materialization rebase, and `LoweringCoordinator` owns `lower` policy. The target-semantic namespace-move workflow is delegated to `SemanticRefactoringCoordinator` rather than embedded in the main lowering policy.

A single `VSlicesProjectContext` represents detected project/config/ruleset/lineage roots.

## Semantic conservation and normalization

Unknown semantics fail closed through known VSIR mappings. Traits are unordered capabilities; unknown or duplicate traits fail explicitly.

The TicketCode experiment added the first observed normalization semantic:

```yaml
- normalize:
    target: input.Value
    intrinsic: trim
```

`trim` is recognized by `VSlices.Vsir` as a supported normalization intrinsic. Unknown intrinsic values fail at the VSIR layer before target Ruleset lookup.

The ownership boundary is:

```text
VSIR
  -> defines that trim is a recognized normalization semantic

Tooling / C# lowerer
  -> owns ordered normalization dataflow

Ruleset
  -> owns how intrinsic.trim is materialized for C#
```

The current lowering may repeat a rendered normalization expression in validation and construction. The demonstrated `trim` rule is pure; broader normalization will require an explicit referential-transparency invariant or single-evaluation lowering.

## .NET namespace target context

Default C# namespace derivation now uses:

```text
nearest unique .csproj
  -> evaluated RootNamespace via dotnet msbuild
  -> project-relative VSIR directory path
  -> project namespace path policy
```

Project configuration may exclude organizational-only folders:

```yaml
targets:
  csharp:
    namespace:
      ignore-folders:
        - "Aggregates/*"
        - "Aggregates/**/Entities"
```

Pattern semantics are segment-aware:

```text
*   = exactly one segment
?   = one character within a segment
**  = zero or more complete segments
```

The full pattern establishes matching context; only the terminal matched folder is removed from namespace derivation. `Aggregates/**/*` therefore excludes every descendant folder while preserving `Aggregates` itself.

An explicit `--namespace` remains authoritative.

## Lineage and materialization rebase

Lineage bootstrap remains non-destructive:

```text
existing conventional witness
+ no lineage
+ configured bootstrap
-> compute current deterministic projection
-> store deterministic baseline
-> preserve witness byte-for-byte
-> success
```

A later semantic change can use the stored deterministic baseline for a conservative three-way materialization rebase.

`CSharpRebaser` remains textual. `REB002` means the deterministic change location cannot be established uniquely. `REB004` means the location is known but human and deterministic branches changed the same insertion region differently.

`--resolve deterministic` authorizes only that known textual conflict region. It does not authorize unrelated human-code changes.

## Target-semantic closure with Roslyn

The real TicketCode namespace experiment proved that textual preservation can still produce target-invalid human code when semantic references cross the rebase boundary.

For the observed namespace-move case, `lower` can invoke a separate managed Roslyn companion:

```text
vslices / vslices.exe
  Native AOT coordinator

refactor/VSlices.Targets.DotNet.Refactor.dll
  Roslyn/MSBuildWorkspace semantic analysis
  BuildHost-netcore runtime closure
```

The helper receives the semantic artifact name from VSIR `name:`; it does not infer symbol identity from the `.vsir` filename.

The workflow is:

```text
textual candidate
  -> detect known namespace move
  -> ask before potentially expensive Roslyn analysis
  -> resolve original INamedTypeSymbol
  -> discover exact semantic references
  -> prepare conservative rewrites
  -> validate baseline compilation
  -> validate proposed compilation
  -> stage files
  -> show blast radius
  -> ask separately before human-code mutation
  -> re-check SHA-256 preconditions
  -> transactionally commit human files + lineage
```

Failure to obtain a Roslyn `Compilation` is a validation failure, not a successful validation. Existing compiler errors, invalid proposals, unrewritable references, changed preconditions, or transaction failure all stop without intentionally advancing lineage independently.

`rebase` remains the textual primitive. The direct `rebase` command does not promise the project-wide target-semantic closure performed by `lower`.

## Roslyn companion installation health

A complete installed companion means both:

```text
refactor/VSlices.Targets.DotNet.Refactor.dll
refactor/BuildHost-netcore/Microsoft.CodeAnalysis.Workspaces.MSBuild.BuildHost.dll
```

Startup health, same-build self-update repair, archive validation, staging validation, and the Windows installer share this completeness rule. A root helper DLL without `BuildHost-netcore` is incomplete and repairable through `vslices update --self`.

## Ruleset lifecycle

`init` and `update --ruleset` share source materialization and snapshot installation:

```text
materialize source
-> prepare selected target
-> validate prepared snapshot through target loader
-> atomic replace / rollback
```

C# snapshot validation rejects broken loader state before swap.

## Update surfaces

Atomic surfaces remain:

```text
vslices update --self
vslices update --ruleset
```

Plain `vslices update` and combined updates remain intentionally undefined.

## Validation evidence

The preview line now includes regression coverage for:

- normalization representation and unknown intrinsic rejection;
- ordered normalization dataflow and external `intrinsic.trim` realization;
- evaluated `RootNamespace` and namespace path policy including recursive `**`;
- conservative rebase and explicit conflict resolution;
- Roslyn semantic blast-radius planning and fail-closed compilation validation;
- explicit analysis and mutation authorization;
- transactional source + lineage commit;
- complete Roslyn companion packaging and health checks;
- Linux, win-x64 and win-arm64 Native AOT packaging.

## Explicit non-scope

This preview still does not add:

- new domain classifications beyond the observed value-object subset;
- normalization intrinsics beyond `trim`;
- new target languages;
- interpretive lowering;
- Git-history ancestry reconstruction or a provenance graph;
- aggregate `vslices update` semantics;
- generic semantic repair of arbitrary compiler failures;
- semantic refactorings beyond the observed namespace move;
- non-interactive semantic-refactoring approval policy;
- namespace pattern negation/priority/regex semantics;
- Roslyn workspace-scope optimization that could reduce blast-radius completeness;
- configurable terminal themes.

The next work after this PR should start from a fresh consumer boundary rather than extending these mechanisms speculatively.
