# VSlices Tooling v0.2.0 release line

This document reconstructs the `feat/0.2.0-preview` line that is being promoted as **VSlices Tooling v0.2.0**. The filename is retained because it is the historical release-line document; the contract described here is the final v0.2.0 candidate, not the earlier preview snapshot.

The release grew from concrete Ticket Support / Identities witnesses rather than from a speculative language roadmap.

The governing guarantees are:

> Lowering may complete implementation detail. Lowering must not complete missing semantics.

> Semantic structure must be represented or explicitly rejected; it must never disappear silently.

> Tooling owns the constrained rule language. Rulesets own the target vocabulary expressed through that language.

## Release sequence

The release line was hardened through four consumer-driven Tooling PRs:

```text
tooling #4

  -> identifier/equality lowering
  -> trusted lineage and non-destructive bootstrap
  -> Ruleset lifecycle hardening

#5
  TicketCode
  -> normalize trim
  -> evaluated .NET target context
  -> conservative three-way rebase
  -> Roslyn namespace semantic closure
  -> namespace path policy

#6
  Risk negative control
  -> semantic admission != target realization
  -> project-owned .vslices/extensions
  -> replaceable .vslices/ruleset
  -> explicit validation environment

#7
  SrvIdentityId / Location / StreetExtension / Name /
  IdentityType / SrvIdentity / TicketTrayFilter
  -> progressive authoring
  -> canonical parser boundary
  -> broader executable semantic surface
  -> structural semantic types
  -> representation expressions
  -> intrinsic refinement bindings
  -> project lowering
  -> TicketTrayFilter closure without implicit flattening

  -> enforce the same guarantees across every existing route
```

Companion target knowledge was accumulated in `vslices/ruleset` #1 through #4. The intrinsic-refinement language amendment discovered by `StreetExtension` is in `vslices/intermediate-representation#1`.

## Public CLI surface

```text
vslices init

vslices new vsir <artifact>
vslices discovery vsir <artifact>
vslices update vsir <artifact> ...
vslices search ...

vslices transpile <artifact>
vslices rebase <artifact>
vslices lower <artifact-or-project>

vslices update self
vslices update ruleset

vslices --version
vslices -v
```

`update` is a command group. Legacy flag-shaped updater aliases are not part of the v0.2.0 contract.

## Progressive authoring

`new vsir` creates only:

```yaml
vsir: 0.1
name: <artifact>
```

Further knowledge is authored through:

```text
new -> discovery -> update -> discovery -> ...
```

`discovery` exposes the current semantic frontier and structured value grammar. `update` applies advertised semantic/metadata mutations atomically.

All mutation paths now converge on one candidate-validation boundary before persistence:

```text
mutation intent
  -> syntax-preserving enrichment when required
  -> candidate semantic document
  -> canonical parser + active validation environment
  -> persist only if present assertions are valid
```

Legitimate incompleteness remains writable. A malformed/unknown assertion that is already present is not hidden by incompleteness and cannot be persisted by a special mutation route.

Searchable `tags` remain operational metadata; semantic `traits` remain constrained capabilities.

## Canonical conformance versus public authorability

The fully proven public authoring envelope remains:

```text
kind: domain-type
shape: product
classification: value-object | identifier
traits: transform | identifier | refined
```

Executable parser/lowering coverage is broader. Real `sum`, `maintained`, and aggregate-root-sum witnesses conform and lower, while their end-to-end public discovery/update authoring path remains deliberately gated.

Therefore:

```text
canonical conformance
  = VSIR parser/validator + semantic validation environment

public authorability
  = what discovery/update can currently guide
```

An artifact may simultaneously have missing required paths and a present invalid assertion. Discovery preserves both pieces of evidence.

## Shared structural guarantees across canonical forms

Product, sum and maintained parsers remain specialized, but now share strict structural readers for obligations that cannot have shape-specific meaning:

- non-scalar semantic mapping keys fail closed;
- malformed/non-scalar explicit `from` values fail closed;
- `from` and `mapping` are mutually exclusive for one representation coordinate;
- wrong structural field shape is not silently reinterpreted as absence.

This extraction was evidence-driven by real divergence between the specialized parsers; it is not a universal/reflexive parser redesign.

## Semantic construction and representation

Current construction forms exercised by the corpus include:

```text
normalize
ensure
resolve
apply
refine
```

Current representation expressions include:

```text
stringify
represent
select
map
intrinsic
```

Semantic composition remains explicit. A target convenience does not authorize an unstated equivalence.

Structural semantic types are represented as semantic constructors, for example:

```yaml
optional: ProjectReference
sequence: StreetExtension
```

Tooling owns the structural mechanism; Ruleset owns C# realization such as `Option<{value}>` / `Seq<{value}>`.

## TicketTrayFilter closure

The original question compared:

```text
semantic source
  Option<X.Repr>

historical Query-facing C# witness
  nullable scalar coordinates
```

The final normalized VSIR explicitly preserves optionality and projection:

```yaml
ProjectReference:
  type:
    optional: ProjectReference.Repr
  mapping:
    represent: state.ProjectReference
```

No authority justified an implicit `flatten-single-field` relation. v0.2.0 therefore closes the experiment by preserving the explicit semantic structure rather than teaching Tooling to guess a historical convenience shape.

## Rulesets and project semantic extensions

```text
.vslices/ruleset/
  source-owned installed target knowledge
  replaceable by init --force / vslices update ruleset

.vslices/extensions/
  project-owned semantic extension overlay
  preserved by Ruleset lifecycle
```

Project extensions can co-locate semantic admission and target realization while keeping the authorities distinct. Target rules use exact bindings contracts: placeholder declarations, template use and render-time values must agree exactly.

## .NET target context

Default namespace context uses:

```text
nearest unique .csproj
  -> evaluated RootNamespace through MSBuild
  -> project-relative artifact path
  -> configured namespace path policy
```

An explicit `--namespace` overrides only namespace derivation; it does not discard an already discoverable project identity. Nominal type resolution therefore remains available.

Nominal dependencies are discovered through a semantic-model traversal, including nested semantic types and sum variants, rather than through a root-field-only list maintained by the .NET adapter.

## Lineage and materialization rebase

First lineage bootstrap is non-destructive:

```text
existing conventional human witness
+ no lineage
+ configured bootstrap authority
-> compute deterministic projection
-> store deterministic baseline
-> preserve human witness byte-for-byte
```

Later change:

```text
previous deterministic baseline
+ human witness
+ next deterministic projection
-> conservative three-way rebase
```

`CSharpRebaser` remains textual. `REB002` means deterministic location cannot be established uniquely. `REB004` means the location is known but human and deterministic branches changed the same region.

`--resolve deterministic` authorizes only that known textual conflict.

Output routing is consistent across bootstrap paths. With `--stdout`, bootstrap/status evidence goes to stderr while stdout receives the preserved human materialization requested by the caller. Operational lineage may still be established; the human file remains unchanged.

## Project lowering

`vslices lower <project>` evaluates artifacts under one coherent project/Ruleset/extensions/target environment and preserves explicit per-artifact outcomes:

```text
Lowered
Unsupported
Failed
```

Unsupported semantic/target surface can coexist with successfully lowered artifacts and does not automatically make the batch fail.

Target-toolchain, environment, IO and orchestration failures remain failures even if processing continues. If any such failure occurs, the global project command exits non-zero. This makes project lowering safe to consume from automation without treating a real MSBuild/Roslyn failure as “not supported”.

## Target-semantic closure with Roslyn

The TicketCode namespace experiment proved that successful textual rebase can still leave target-invalid semantic references elsewhere in human code.

The observed .NET closure remains a separate managed companion:

```text
vslices / vslices.exe
  Native AOT coordinator

refactor/VSlices.Targets.DotNet.Refactor.dll
  Roslyn/MSBuildWorkspace companion
```

The workflow preserves separate authority for expensive analysis and human-code mutation, validates baseline/proposed compilation, rechecks source preconditions, and commits source + lineage transactionally.

Failure to obtain a Roslyn `Compilation` is a verification failure, not success.

## C# realization hardening

Generated state access and literal encoding are explicit target responsibilities:

- stored state references resolve to their actual storage member;
- derived state references resolve through the derived accessor rather than an invented backing field;
- C# string literals use shared escaping for newlines and other control characters.

The test suite now includes a generated-materialization compilation witness against Tooling's pinned Framework submodule. The witness combines derived state projection and a multiline failure message so a textual `Assert.Contains` cannot hide an invalid generated program.

## Distribution and updater contract

Roslyn remains outside the Native AOT coordinator. A complete distribution contains the executable plus the managed companion runtime closure, including `BuildHost-netcore`.

Self-update and Ruleset-update are independent command surfaces:

```text
vslices update self
vslices update ruleset
```

The release workflow installs the published Windows artifact and runs the **current** updater syntax. It also checks updater-specific output postconditions; exit code zero by itself is not accepted as evidence because a help path can also return zero.

## v0.2.0 release-hardening regression laws

The final release review added explicit evidence for:

1. invalid mutation rejected without file change;
2. structural shorthand preserved when enriched;
3. legitimate incomplete mutation remains writable;
4. same malformed semantic structures rejected across canonical forms;
5. present invalid assertions remain visible beside missing knowledge;
6. namespace override preserves .NET project identity;
7. nominal dependency traversal includes variant-only dependencies;
8. generated derived-state/multiline-failure materialization compiles;
9. project lowering preserves Unsupported versus Failed and returns non-zero on injected toolchain failure;
10. lineage bootstrap honors `--stdout` and preserves the human witness;
11. release updater smoke proves the updater actually executed.

## Explicit v0.3.0+ questions

The following remain deliberately outside this release:

- full public authoring parity for witnessed `sum`, `maintained`, entity/aggregate-root forms;
- additional semantic vocabulary without new consumer evidence;
- invocation-local numbered selection for ambiguous artifact symbols;
- lowering multiple explicitly selected artifacts in one invocation;
- folder/scoped/batch lowering beyond single-artifact and whole-project subjects;
- a stable CLI visual language before standardizing colors/spinners/progress markers;
- generic compiler repair or additional semantic-refactoring families;
- stronger provenance across Tooling/Ruleset evolution and Git history;
- aggregate updater ordering/recovery semantics;
- interpretive lowering.

The v0.2.0 release closes by making already-accepted guarantees consistent across the current surface, not by expanding that surface speculatively.
