## Available command groups

```text
vslices init
vslices --version
vslices -v

vslices update self
vslices update ruleset
vslices update docs-standard
vslices update template-standard

vslices new vsir <artifact>
vslices discovery vsir <artifact>
vslices update vsir <artifact> ...

vslices new document <name> --kind <type>
vslices discovery document <name>
vslices update document <name> --question-id <selection> --answer "<markdown>"

vslices new nexus <name> --kind <type> --target <target>
vslices discovery nexus <name>
vslices update nexus <name> --question-id <selection> --answer "<answer>"

vslices new continuity-path <name> --kind <type> --target <target>
vslices discovery continuity-path <name>
vslices update continuity-path <name> --question-id <selection> --answer "<answer>"

vslices new support-note <name> --kind <type>
vslices discovery support-note <name>
vslices update support-note <name> --question-id <selection> --answer "<answer>"

vslices search --filter tags:contains:<value>
vslices search --filter kind:equals:<family>

vslices transpile <artifact>
vslices rebase <artifact>
vslices lower <artifact-or-project>
```

The command is **`vslices search`**, with `--filter` as an option; no separate top-level `vslices filter` is asserted. `vslices update` is a command group, **not** an aggregate no-argument updater.

## Project bootstrap and documentary authoring

1. `vslices init` establishes project-local `.vslices/config.yaml` and `.vslices/.ignore`; it does **not** automatically imply all knowledge standards are installed.
2. `vslices update docs-standard` installs/refreshes documentary definitions; `vslices update template-standard` installs/refreshes materialization definitions; `vslices update ruleset` is the independent lowering-knowledge path. Initialization supports convenience origin options that delegate to these update operations.
3. `documents.route` configures user-facing product-document placement (commonly `docs/`), distinct from `.vslices/` operational policy, installed snapshots and lineage. Explicit artifact paths can override route selection where supported.
4. Work with a knowledge artifact through `new → discovery → update → discovery`. `discovery` provides the current choices, ephemeral selection paths and suggested commands; do not guess stable question identities from displayed indices.

## Knowledge-artifact families

| Family | Implemented capabilities |
| --- | --- |
| **Document** | Docs Standard-defined question trees, progressive authoring, one/many repeated AnswerInstances, scoped descendants, reconstruction using the installed Template Standard. |
| **Nexus** | Composition of documentary perspectives; open questions, recommendations, explicit reciprocal artifact relations, creation of linked Documents/Nexus artifacts. |
| **Continuity Path** | Navigable graph, node-local recommendations, question updates, creation of linked Documents/Nexus artifacts; compact graph summary in discovery while preserving the Mermaid diagram in Markdown. |
| **Support Note** | Definition-driven small notes (currently promoted Draft, Result, Validation and Risk forms), complete small question surface, optional relations. |

**Layout integrated from PR #11:** Nexus, Continuity Path and current relationally authored Support Note surfaces can materialize as `<artifact>/README.md`. Name-based resolution supports this directory-backed layout; recommendation-created children can be placed within their source surface, and reciprocal links are relative to the actual artifact paths.

Operational `metadata.tags` supports creation/set/add/remove, remains nonsemantic and is searchable across all four knowledge families as well as VSIR. Search supports indexed properties including `kind`, `type`, `scope`, `target`, `status`, and `tags` where available, excluding installed `.vslices` knowledge snapshots from consumer artifact results.

## VSIR and executable realization

v0.2.0-era VSIR capabilities remain: progressive `new/discovery/update` authoring, semantic conformance checks, C# deterministic `transpile`, project-aware `lower`, conservative `rebase`, lineage, target context, Ruleset/extension-based realization and guarded Roslyn namespace-move repair. Canonical parsing/lowering covers more forms than the narrower public interactive authoring envelope; do not infer parity for every admitted VSIR form.

## Known limits and authority

- `vslices/docs-standard` owns documentary semantics and question identities; `vslices/template-standard` owns document materialization/reconstruction vocabulary; `vslices/tooling` owns executable project configuration, acquisition, CLI authoring/search, relations and writes.
- Structured selections like `2.1` are ephemeral discovery navigation, not persisted semantic identity.
- Not all Markdown variations, semantic-subject identities, per-instance repeated-answer edits/removals, relation ontologies or Template Standard materialization variants are supported.
- Some Nexus/Path relational front matter, associated tables and graph materialization are still realized inside Tooling pending a fuller Template Standard contract.
- Handled failures can roll back coordinated writes; this does not guarantee crash-atomic multi-file filesystem transactions.
- `v0.3.0-preview` integration does not imply the separate modern Framework migration proposals were merged.
