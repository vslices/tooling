# VSlices Tooling v0.1.1-preview

`v0.1.1-preview` is a distribution and release-pipeline patch over the `v0.1.0-preview` baseline.

It does not expand VSIR semantics or add a new lowering mechanism. The purpose of this patch is to make the existing Windows installation and self-update contract work on Windows ARM64 as well as Windows x64, while also improving the development and release pipeline discovered during the first patch validation.

## Triggering evidence

The first public bootstrap attempt on a Windows ARM64 machine failed because `install.ps1` explicitly accepted only x64 even though the CLI self-update runtime resolver already understood `win-arm64`.

This exposed a mismatch between three parts of distribution:

```text
runtime detection
release assets
bootstrap installation
```

`v0.1.1-preview` aligns them.

During validation of that patch, the repository also exposed duplicate GitHub Actions work: feature-branch pushes and pull-request events triggered the same CI suite independently. With the Windows Native AOT matrix, one logical PR update could therefore create duplicate `test`, `win-x64`, and `win-arm64` checks.

The same validation cycle exposed another development cost: testing a new CLI command on a real machine required publishing a tagged prerelease or manually moving binaries around. PR builds now provide an installable intermediate state without turning every development build into a Git tag or GitHub Release.

## Changes

The Windows PowerShell bootstrap now resolves the current operating-system architecture and selects one of:

```text
win-x64
win-arm64
```

The release workflow publishes Native AOT archives and SHA-256 checksums for both Windows RIDs:

```text
vslices-win-x64.zip
vslices-win-x64.zip.sha256

vslices-win-arm64.zip
vslices-win-arm64.zip.sha256
```

The existing runtime resolver already supports both x64 and ARM64 runtime identifiers.

CI now treats a pull request as one logical concurrency scope. Feature branches are validated by `pull_request`, while `push` CI is reserved for `main` and release tags. Within a PR, a newer commit cancels the previous in-progress run:

```yaml
concurrency:
  group: ci-${{ github.event.pull_request.number && format('pr-{0}', github.event.pull_request.number) || format('{0}-{1}', github.event_name, github.ref) }}
  cancel-in-progress: true
```

The `test`, `win-x64`, and `win-arm64` jobs remain parallel inside that single logical run; the change removes duplicated push/PR executions rather than serializing useful platform validation.

The same CI workflow is also the authority for scheduled nightly validation and release-tag validation. It can be triggered by:

```text
pull_request
push to main
nightly schedule
manual workflow_dispatch
v* tag
```

This keeps the validation operations identical across PR, nightly, and tag contexts instead of maintaining a separate nightly suite that could drift from what PRs actually prove.

## Installable PR builds

Every pull-request CI run publishes Native AOT artifacts for:

```text
linux-x64
win-x64
win-arm64
```

A build identity is derived only from GitHub context:

```text
build<pr-number>.<run-number>
```

For example:

```text
build2.154
```

The RID-specific Actions artifacts are named:

```text
build2.154-linux-x64
build2.154-win-x64
build2.154-win-arm64
```

The build identity is intentionally not tied to a future release version. CI uses a SemVer-compatible assembly representation such as `0.0.0-build.2.154`, but the user-facing identity remains `build2.154`.

A project may follow the newest successful build of a PR with:

```yaml
updates:
  source: https://github.com/vslices/tooling
  channel: build
  pull-request: 2
```

`vslices update --self` resolves the newest successful CI run for PR #2 automatically, so the run number is never copied into configuration by hand.

PR build artifacts are a developer surface rather than a public release surface. Downloading GitHub Actions artifacts requires GitHub authentication; the updater accepts `GH_TOKEN`, `GITHUB_TOKEN`, or an authenticated `gh` session.

Published versions remain deliberate tag decisions:

```text
PR builds
  -> build2.154
  -> build2.155
  -> build2.156

human release decision
  -> tag v0.1.1-preview
```

No PR build creates a Git tag or GitHub Release.

## Release tags

For a release tag, the relationship is:

```text
v* tag
  -> CI validation: test + Native AOT platform checks
  -> Release CLI workflow: build/package/publish release assets
```

The release workflow remains responsible for producing and publishing release artifacts; CI remains responsible for proving the code and supported publication RIDs are valid.

## Validation

Before release, CI must prove that Native AOT publication succeeds for both `win-x64` and `win-arm64` on the Windows build environment.

The release workflow continues to execute the published bootstrap end to end on the hosted Windows x64 runner. ARM64 execution itself requires an ARM64 Windows environment and is therefore validated by a real ARM64 installation after publication.

The CI trigger/concurrency contract must also demonstrate that a feature branch with an open PR creates one current PR run rather than duplicate push and pull-request runs, and that a newer commit supersedes an older in-progress run for the same PR.

A successful PR run must publish the three RID-specific `build<pr>.<run>-<rid>` artifacts. The `build` self-update channel must resolve the newest successful run for the configured PR and preserve the same SHA-256 verification used by release updates.

Nightly and `v*` tag runs execute the same CI job set used by pull requests. A release tag additionally triggers the release workflow that packages and publishes the verified RID-specific artifacts.

## Explicit non-scope

This patch does not add:

- `vslices interpretate`;
- new VSIR structures;
- new lowering rules;
- new target languages;
- macOS distribution;
- Linux ARM64 distribution;
- a graphical installer.

Those remain independent evolutionary steps.
